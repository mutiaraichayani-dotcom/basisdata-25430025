## A. Tujuan Pengujian

Pengujian dilakukan untuk memastikan data Klinik Mutiara dapat dimasukkan dan ditampilkan dengan benar, serta memastikan constraint pada tabel bekerja sesuai rancangan. Pengujian juga mencatat aturan yang belum dapat ditegakkan oleh struktur database saat ini sebagai *design debt* untuk diperbaiki pada Modul 14.

## B. Ringkasan Skenario Pengujian

Terdapat 10 skenario: 2 pengujian positif, 7 pengujian negatif terhadap constraint, dan 1 pengujian *design debt*. Pengujian negatif diharapkan ditolak oleh database. Pada pengujian *design debt*, justru ditemukan bahwa data yang seharusnya ditolak masih dapat masuk.

## C. Rincian Pengujian

### UJ-01 — Pengujian positif relasi pemeriksaan

**Tujuan:** Memastikan data pemeriksaan terhubung dengan data pasien dan dokter.

```sql
SELECT
    p.no_pemeriksaan,
    ps.nama_pasien,
    d.nama_dokter,
    p.tanggal_pemeriksaan,
    p.diagnosis
FROM pemeriksaan p
JOIN pasien ps ON p.no_pasien = ps.no_pasien
JOIN dokter d ON p.kode_dokter = d.kode_dokter
ORDER BY p.tanggal_pemeriksaan
LIMIT 10;
```

**Hasil yang diharapkan:** Query berhasil dan menampilkan nomor pemeriksaan, nama pasien, nama dokter, tanggal, serta diagnosis.

### UJ-02 — Pengujian positif relasi resep

**Tujuan:** Memastikan tabel resep, pemeriksaan, pasien, detail resep, dan obat saling terhubung.

```sql
SELECT
    r.no_resep,
    p.no_pemeriksaan,
    ps.nama_pasien,
    o.nama_obat,
    dr.jumlah_obat,
    dr.aturan_penggunaan
FROM resep r
JOIN pemeriksaan p ON r.no_pemeriksaan = p.no_pemeriksaan
JOIN pasien ps ON p.no_pasien = ps.no_pasien
JOIN detail_resep dr ON r.no_resep = dr.no_resep
JOIN obat o ON dr.kode_obat = o.kode_obat
ORDER BY r.no_resep;
```

**Hasil yang diharapkan:** Query berhasil menampilkan data resep beserta pemeriksaan, pasien, dan obat.

### UJ-10 — Design debt: nomor identitas pasien ganda

**Tujuan:** Menemukan aturan yang belum dapat ditegakkan oleh struktur database saat ini.

**Acuan:** Aturan bahwa satu nomor identitas hanya boleh dimiliki satu pasien. Constraint `UNIQUE` pada kolom `pasien.no_identitas` belum tersedia.

Pengujian dilakukan dalam transaksi agar data percobaan dapat dibatalkan.

```sql
START TRANSACTION;

INSERT INTO pasien
(no_pasien, no_identitas, nama_pasien, tanggal_lahir, alamat, no_telepon)
VALUES
('PS-UJI', '1871051201010001', 'Pasien Pengujian',
 '2000-01-01', 'Jl. Pengujian No. 1', '081234567890');

SELECT no_pasien, no_identitas, nama_pasien
FROM pasien
WHERE no_identitas = '1871051201010001';

ROLLBACK;
```

**Hasil yang diharapkan dari aturan bisnis:** Database seharusnya menolak nomor identitas yang sudah digunakan.

**Hasil aktual:** Pengujian menunjukkan bahwa INSERT diterima dan SELECT menampilkan dua pasien dengan nomor identitas yang sama, yaitu `PS-001` (Ayu Lestari) dan `PS-UJI` (Pasien Pengujian). Dengan demikian, pengujian aturan keunikan ini gagal karena constraint belum diterapkan.

**Tindak lanjut Modul 14:** Tambahkan constraint `UNIQUE` pada kolom `no_identitas` setelah memastikan tidak ada data identitas ganda pada data permanen.

**Catatan:** Perintah `ROLLBACK` digunakan untuk membatalkan data percobaan. Pastikan perintah tersebut sudah dijalankan setelah mengambil screenshot.

## D. Kesimpulan

Berdasarkan rancangan pengujian, database Klinik Mutiara diperiksa melalui pengujian relasi data, constraint CHECK, dan Foreign Key. Pengujian *design debt* menemukan bahwa nomor identitas pasien masih dapat digunakan lebih dari satu pasien karena kolom `no_identitas` belum memiliki constraint `UNIQUE`. Aturan tersebut dicatat untuk diperbaiki pada Modul 14.

**Catatan pelaporan:** Lengkapi kolom atau keterangan hasil aktual untuk UJ-01 sampai UJ-09 berdasarkan pesan dan hasil yang benar-benar tampil di phpMyAdmin. Jangan menyatakan pengujian berhasil apabila hasilnya belum diperiksa.
